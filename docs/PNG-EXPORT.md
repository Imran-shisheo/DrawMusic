# PNG still-image export

F16 now has an original, genuine PNG path. `ImageExportPort` accepts one immutable document snapshot; `FileImageExportAdapter` rasterizes the document at either 640×800 or 1080×1350. The fixed 4:5 document aspect and normalized geometry match the current editor and video contract. No widget controls, selection overlay or playback cursor are included, and no score compilation is required for a still image or empty drawing.

The background is included by default through the shared background renderer: solid/opacity, linear/radial gradients and content-addressed private photo assets with crop/rotation/mirror settings. Missing or damaged photo assets fail the normal export instead of producing a silently substituted image. The explicitly selected transparent option omits the entire background and preserves ink alpha; it can also recover artwork from a document whose background asset is unavailable. Preview volume and musical settings do not affect still-image pixels.

The renderer records one bounded picture and one raster image. Maximum output pixel storage is 1080×1350×4 = 5,832,000 raw bytes, in addition to the immutable document/picture, compressed PNG bytes and a bounded decoded background image. This is an allocation bound for those buffers, not a measured process RSS or physical-device performance claim. It never accumulates video frames. Image, picture, background-image and unfinished recorder resources are disposed on success, error and cancellation.

The UI exposes size, transparent background, busy/progress, Cancel and localized outcomes. Empty artwork requires an explicit localized confirmation; canceling that prompt starts no job. Cancellation is checked before rendering, between stroke batches, after native raster/PNG encoding, before/after writing and after atomic rename. An incomplete or canceled job removes both its temporary file and any just-published target. Cancellation cannot interrupt the middle of a single native raster/PNG encoding call, but its result is discarded afterward. Encoded dimensions and PNG signature/IHDR are checked before publication. Library recording occurs only after successful file creation.

PNG files use `image/png` throughout discovery, persistent metadata, exact-byte rename, delete/Undo, native Open, explicit public Save and the native Share sheet. The library decodes the actual PNG with a bounded thumbnail cache width rather than reconstructing a potentially changed document for its preview. Android public saving retains MediaStore publication/copy verification and the legacy document-provider flow; it does not request broad storage permissions. A chooser launch or Share result does not prove recipient delivery.

## Evidence

`test/png_export_test.dart` contains eight meaningful cases. A separate PNG parser validates chunk CRCs, decompresses IDAT and independently reconstructs scanline filters to inspect dimensions, RGB/alpha pixels, backgrounds, normalized ink and the absence of the cursor. Tests cover both sizes, Smooth/Pixel, transparency, gradients, real hash-addressed photo/crop/rotation, missing-image recovery, exact snapshot preservation, library restart/rename/delete/Undo, six cancellation stages (including after rename), invalid size/raster and filesystem failures. The eighth case verifies exact native Open/Save payloads and an honest canceled destination result. All eight focused Flutter tests passed in the selected Linux cloud environment on 26 October 2026; the final checkpoint records its source commit and broader gate separately.

`test/png_library_widget_test.dart` contains two passing focused widget cases: the empty-image confirmation/Cancel starts no job, and a real PNG thumbnail supports explicit Open/Share/public Save/Unicode Rename/Delete/Undo with recording platform ports. Full-check evidence is recorded separately from these focused results.

`PngExportRuntimeTest.publicPngCopyPreservesPixelsDimensionsAndEveryByte` adds actual Android PNG decode and MediaStore-copy assertions. Compilation is not runtime acceptance. Hosted emulator execution and physical receiving-app behavior must be reported separately in the checkpoint evidence. Physical image viewers, document providers, sharing recipients and camera behavior remain device acceptance work.
