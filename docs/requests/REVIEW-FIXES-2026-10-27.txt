2. FIX: ERASING NEAR THE POINT CAP THROWS AN EXCEPTION

Relevant code:
- lib/features/editor/presentation/canvas.dart, approximately lines 250–257
- lib/features/editor/presentation/editor.dart, approximately lines 974–978
- lib/creative_document/document.dart, approximately line 213
- lib/features/editor/domain/history.dart: eraseAt

Verified behavior:
The eraser clips segments into fragments. This can ADD intersection endpoints.

A valid 99,999-point document can become 100,001 points after an erasure. The canvas commits the erased geometry without checking capacity; the editor constructs a ProjectDocument and throws:
FormatException: Invalid project

The same issue occurs at 100,000 → 100,002 points.

Minimal reproduction:
- Create a two-point horizontal stroke from (.1,.5) to (.9,.5).
- Add a second stroke containing enough points outside the eraser region,
  for example at (.1,.1), to bring the document to 99,999 or 100,000 points.
- Call eraseAt(document.strokes, InkPoint(.5,.5), .03).
- Construct document.copyWith(strokes: erased).
- Observe that the added clipping endpoints exceed the point cap.

This is relevant to supported older/reopened dense drawings. A dense
outside zigzag that cannot simplify also makes the state reachable.

Required fix:
- Validate eraser output before changing committed canvas state.
- Apply safe, bounded simplification if appropriate.
- If valid output cannot fit, preserve the prior document and give
  actionable feedback instead of throwing.
- Do not silently discard unrelated geometry or musical content.
- Keep one eraser gesture as one undoable edit.
- Do not show a successful save for a rejected operation.

Tests:
- Near-cap and exactly-at-cap documents
- Erasure that increases point count
- Repeated erasure gestures
- No-op erasure
- Undo/redo
- Save/reopen after successful erasure
- Rejected operation preserves original document and usable input
- Existing geometry-to-score invariants remain intact

6. FIX: IOS PAUSE CAN DISCARD A LIVE AUDIO REVISION

Relevant code:
- ios/Runner/DrawMusicAudio.swift:
  render-side revision adoption around line 138
  audiblePosition around lines 183–188
  pause around lines 199–202
- lib/features/editor/presentation/editor.dart:
  resume queue logic around lines 421–425

Source finding:
After the render thread adopts a queued revision, it clears pending.
During output latency, audiblePosition can still refer to the previous
revision. Pause assigns that old audible loop back to loop, discarding
the newly adopted target.

Dart already considers the new revision queued, so Resume may not resend
it. Old audio can persist until another edit or Replay, with an update
indicator that does not resolve.

Required fix:
- Preserve the newest desired/queued revision while retaining a correct
  audible pause position.
- Define native current revision, target revision and paused phase
  consistently.
- Reconcile native and Dart target state where needed.
- Preserve the documented tempo/loop-boundary update policy.
- Maintain one engine/session and safe rapid pause/resume behavior.

Add meaningful native scheduling tests covering:
- Pause just before and after a revision boundary
- Rendered target ahead of audible position
- Positive output latency
- Resume without another edit
- Repeated edits and tempo changes
- Accurate status/current/target revision reporting
- No lost updates or permanently pending indicator

Do not treat mocked Dart channel payload tests as proof that this native
state machine works.
