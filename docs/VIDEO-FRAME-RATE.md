# MP4 frame-rate options and profiling scope

The video export sheet offers independently selected dimensions (HD 1080×1350 or compact 640×800) and **30 or 60 FPS**. The default remains 30 FPS. The saved document and its musical snapshot are unaffected by selecting export options. Frame rate is forwarded explicitly through `VideoExportPort`, validated by Dart/native adapters, returned in encoder metadata and persisted as `ExportArtifact.framesPerSecond` by the export library. Historical entries lacking that optional field remain readable.

The Android implementation renders genuine extra frames at 60 FPS: both input timestamps and encoder format use the selected rate. It does not duplicate the same 30 FPS schedule under a different metadata label. The drawing cursor position derives from each frame's timestamp and the frozen score's duration. Audio is the same immutable PCM rendered by preview/WAV; AAC alignment and release-tail handling are unchanged. Requested bitrate scales with frame rate (HD 4/8 Mbps, compact 2/4 Mbps for 30/60), and unsupported codec configuration remains a real failure with no successful artifact.

Memory is bounded by the frame renderer and native codec queues, not video duration or frame count. `DocumentFrames` reuses one ARGB bitmap and one pixel array; one input YUV image is filled and closed before submitting the next frame. For the compact fixture the bitmap and array account for 4,096,000 bytes, excluding decoded photo storage, PCM, codec queues and platform overhead. This accounting is not a whole-process memory or physical-device performance claim. Existing cancellation, 30-second codec-stall detection, progress and temporary-file cleanup apply to both rates. Cancellation regression coverage runs for both 30 and 60 FPS.

`compactSixtyFpsUsesRealCodecTimestampsAndReportsBoundedRendering` performs a real API 35 Android codec export and independently reads the resulting file with MediaExtractor. It checks H.264/AAC, 640×800, nominal 60 FPS, strictly increasing approximately 16,667 µs sample timestamps, sample count and A/V duration agreement within one frame (plus 2 ms container rounding allowance). The test writes `fixture-video-60.mp4` and `video-60-profile.json` to the app cache. The report contains elapsed export time, sample timing, video/audio durations and initial/peak-sampled/final whole-process PSS. A failed test writes `passed:false`; report existence alone is not acceptance. Native unsupported-24-FPS coverage rejects the request before creating partial files.

Current source adds these runtime checks; compilation or widget tests alone do not establish that the codec profile has passed. Consult DEVELOPMENT-STATUS.md and the exact source/run artifacts for executed results. A cloud emulator timing measurement does not establish physical 60 FPS export feasibility on every device, release drawing FPS, audio latency or iOS behavior. If the device's encoder rejects 60 FPS, the working 30 FPS option remains available. Physical playback/export on representative devices remains pending.

The iOS adapter accepts the same option and contains a bounded writer implementation, but Linux checks cannot compile or profile AVFoundation. Its 30/60 FPS codec, timestamps, memory and cancellation behavior require Mac/simulator/device validation; no iOS profile is inferred from Android results.

Accepted Android source `c721ce6d508ebde63b318859e3931342600f79f6` passes the real 60 FPS test and independent FFmpeg inspection in [Actions 40329847034](https://github.com/Imran-shisheo/DrawMusic/actions/runs/40329847034). See video-60-profile.json and video-60-inspection.json in [runtime evidence](https://github.com/Imran-shisheo/DrawMusic/actions/runs/40329847034/artifacts/12657186456) for actual elapsed/PSS/timestamp/A/V values. This closes the compact 640×800/60 FPS emulator profile only. A separate HD 1080×1350/60 FPS profile has not been executed; HD 30 FPS is covered by the original fixture. Representative physical-device reliability and iOS remain open.

Observed accepted compact profile: 317 encoded samples, 16,666–16,667 µs PTS steps, 5,283,333 µs video/5,270,929 µs audio, 16.796 s elapsed and 66,110 KiB peak-sampled process PSS.
