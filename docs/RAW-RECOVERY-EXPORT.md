# Raw recovery export for undecodable projects

A damaged/future project that cannot be decoded still appears in Drafts. Retry attempts to reopen it without replacing its data. **Export recovery data** is an explicit optional capability, independent of musical/image export and the normal export library. It creates a lossless `.drawmusic-recovery.json` envelope and then opens the native share sheet only after the user taps the action. No recipient is selected and no delivery is inferred from the result. Dismissed/unavailable/success outcomes use honest existing messages; failure keeps original files and shows localized guidance. The iPad sharing anchor is supplied.

`RecoveryExportPort` does not expand or break the `ProjectRepository` interface. The real file repository implements it and serializes export against writes/rename/deletion. Each record includes only the original app-generated basename, exact original byte length, independently computed SHA-256 and base64 bytes. The envelope identifies itself as `drawmusic-raw-recovery`, version 1, **not** an editable project, WAV, MIDI or image. Corrupt bytes, unsupported versions, preserved damaged revisions, empty files and interrupted revision `.tmp` files are retained unchanged; there is no attempt to parse, fix or claim their contents are usable.

The operation accepts a validated flat project ID, rejects symlinked project directories/files/destinations, and never scans unrelated app/private paths. It includes all recognized revision, preserved-revision and deletion-marker files. Unexpected filenames, nested directories or unsupported entities cause an explicit failure rather than being silently skipped or exposing unrelated files. At most 200 files and 64 MiB of raw source bytes are allowed; larger input requires a separate recovery approach and is not silently truncated. A streaming base64 writer with awaited flushes provides backpressure; it does not accumulate all raw files or the whole encoded bundle in memory. The base64 envelope can be larger than the 64 MiB raw-byte cap.

Bundles are written beside the project store in app-private `recovery-exports/` through a temporary file and atomic rename. Failed publication removes partial targets/temps. Source files are never renamed or deleted; changed size/mtime during export causes a retryable failure. A successful bundle is retained for the receiving application to read. Photo asset bytes live in a separate content-addressed store and are not silently embedded by this raw-revision export; their IDs/configuration remain in the original revision bytes. This is a support/recovery container, not a complete portable project/archive import format. No automatic re-import or recovery success is claimed.

`test/raw_recovery_export_test.dart` uses real files and independently decodes/rehashes every bundled corrupt/future/preserved/temp payload. It also covers wrong IDs, empty/missing projects, symlink rejection, unsupported files/directories, 200-file/64 MiB limits and actual destination filesystem failure, checking unchanged source bytes and absence of partial output. `test/raw_recovery_widget_test.dart` covers explicit activation, payload/anchor and each sharing result plus failure without exposing diagnostics; its recording share port is widget-only evidence, not physical sharing. Final executed results and source/run links belong in DEVELOPMENT-STATUS.md. Actual receiving-app delivery, physical low-storage and iOS compilation remain separate acceptance work.
